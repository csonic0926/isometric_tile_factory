# Causal interaction — optional method

Use when a loop exists in prose but not in player work, or a second lap feels
identical. Inputs: adopted product, current build/state, proposed complete design,
relevant project standard. No separate method-output file is required.

Walk one concrete initial state: goal -> available alternatives -> commitment ->
actual work -> perceptible response -> persistent consequence -> changed next
choice. Then walk a second lap using that consequence. If a reward never changes
what the player decides/does, it is presentation rather than a causal loop edge.

Group system transitions under real work rather than manufacturing a click per
phase. Put automatic settlement and supporting observation in response/affordance
fields. Check entry knowledge, time advance, cancellation, delay, failure,
recovery and return against the current scene and actual clock/state model.
Draw where targets, controls, obstacles and feedback occur; test whether a player
could discover and perform the work without reading the design's answer.

Revise the one complete design. Its human sections must expose scene/time/cost
choices, not hide them behind a favorable synopsis. Use existing mechanical
validators and independent review; neither diagram count nor this exercise is
acceptance evidence.
